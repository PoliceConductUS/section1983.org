# section1983.org

Static Astro site with AWS infrastructure managed by Terraform.

## Stack

- Astro for site build
- S3 + CloudFront for hosting/CDN
- ACM for TLS certs
- Route53 for DNS
- GitHub Actions for deploys
- Terraform bootstrap stack for all infrastructure

## Local Dev

```bash
npm ci
npm run dev
```

## Build

```bash
npm run build
```

Note: `npm run build` expects Mermaid CLI (`mmdc`) for diagram generation.

## Validate

```sh
npm run validate
```

Runs the format check (`npm run format:validate`), lint, the OpenSpec schema and artifact validation, the type check, the Terraform format and configuration check (`npm run infra:format:validate`), and the unit tests. It needs Terraform installed. The type check (`npm run typecheck`) covers the `.astro` files with `astro check` and the remaining TypeScript and JavaScript with `tsc`. The `Validate` workflow runs it on every pull request.

## Agent Workflow

This repo uses [OpenSpec](https://github.com/Fission-AI/OpenSpec) for intended
behavior, [Superpowers](https://github.com/obra/superpowers) for execution skills,
and the [Superpowers bridge](https://github.com/JiangWay/openspec-schemas) to keep
brainstorming, plans, verification, and retrospectives together in
`openspec/changes/<change-name>/`.

After `npm ci`, inspect the setup with:

```bash
npm run validate:openspec
npm run openspec -- schemas
npm run openspec -- list
```

For a new capability or contract change, use the task branch and worktree from
`AGENTS.md`, then use the OpenSpec skills to create a change, continue its
artifacts, apply the plan, verify it, and archive it. In Codex, start with
`$openspec-new-change`; in Claude Code, use `/openspec-new-change`. Continue with the
corresponding `openspec-continue-change`, `openspec-apply-change`,
`openspec-verify-change`, and `openspec-archive-change` skills. The default schema
is `superpowers-bridge`.

Inspect an existing change with:

```bash
npm run openspec:status -- --change <change-name>
```

Documentation, formatting, tooling setup, and fixes that preserve specified
behavior can proceed directly. The existing content style review, lint, build,
and branch rules still apply.

Imported skill examples are excluded from the site TypeScript compilation, and
imported skills and bridge templates retain their upstream formatting. The bridge
still runs through OpenSpec schema validation.

The OpenSpec CLI is pinned to `2.1.0`, matching `policeconduct.org`. Its project
skills are generated by `openspec init --tools codex,claude --profile custom
--scope project`. The custom workflow set used here is `propose`, `explore`,
`new`, `continue`, `apply`, `sync`, `archive`, and `verify`.

Superpowers is installed in `.agents/skills/`, with the same Claude Code, Hermes,
and shared skill links used by the existing project skills. `skills-lock.json`
records upstream commit `22f0b463e7a5e579904dd6211a520321035526f7` and the skill
hashes. New project skills become available when your agent reloads the checkout.
The bridge schema and templates match `project-template` commit
`741d97a7bc8e4adc56911389cfec25acfc58bcbc`; its source is
[JiangWay/openspec-schemas](https://github.com/JiangWay/openspec-schemas).

### Elephant-Goldfish Model

Use [EGM](https://github.com/google/elephant-goldfish-model) to develop ideas,
draft designs, and review documents with fresh-context reviewers. Its eight
skills and supporting reviewer prompts, standards, and host integrations are
checked into `.agents/egm/`. The bundle is version `0.1.1`, pinned to upstream
commit `70406c4d22cc7ea8299637c2c5b44625c48b3f08`. The skill entries and hashes
are recorded in `skills-lock.json`. Imported files retain upstream formatting.

Codex discovers the skills through `.agents/skills/`; Hermes and the shared
`skills/` directory link to the same files. Claude Code loads the whole plugin
through `.claude/skills/egm`, preserving its reviewer adapters and plugin paths.
Start a new session from this checkout after installation. Claude Code requires
you to trust the checkout before loading its project plugin. See the
[Claude Code loading reference](https://code.claude.com/docs/en/plugins/loading#plugins-shared-through-a-repository).

In Codex, invoke `$egm-review <document-path>`; in Claude Code, use
`/egm:egm-review <document-path>`. The other skills are `egm-brainstorm`,
`egm-draft`, `egm-resolve`, `egm-review-loop`, `egm-lite`, `egm-bootstrap`, and
`egm-drift-report`. Goldfish reviews require a host with fresh-context subagents.

OpenSpec continues to record intended behavior, and Superpowers supplies the
execution workflow. When using EGM for an OpenSpec change, include
`EGM artifact directory: openspec/changes/<change-name>/` in your prompt to keep
its briefs, drafts, and reports with the change.

## Infrastructure

Single Terraform entrypoint:

- `infrastructure/bootstrap`

Run all infrastructure work through these commands:

| Command                         | Use it when                                                                                                                                                                                                                                                                                                                                                                                                           | Changes anything?        |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| `npm run infra:apply`           | You edited the Terraform files or the tracked inputs and want live infrastructure to match. It shows every difference between live infrastructure and the code, refuses destroys nobody approved, asks for `yes`, then applies exactly that.                                                                                                                                                                          | Yes, live infrastructure |
| `npm run infra:diff`            | You only want to see how live infrastructure differs from the code, for example after someone changed a setting in the AWS console. It shows the same differences as `apply` and stops.                                                                                                                                                                                                                               | No                       |
| `npm run infra:refresh`         | A setting was changed outside Terraform and the state should record what is live now. It shows those changes, asks for `yes`, then updates only the state.                                                                                                                                                                                                                                                            | Terraform state only     |
| `npm run infra:add:secret`      | A secret is new or its value changed. Give the names only, for example `npm run infra:add:secret -- SENTRY_AUTH_TOKEN GITHUB_TOKEN`. It asks for each value with hidden input, so the value stays out of the shell history, and stores it in Parameter Store, replacing any existing value. Every PoliceConductUS repository reads the same secrets. Run `infra:apply` afterwards to pass the new value on to GitHub. | Yes, Parameter Store     |
| `npm run infra:outputs`         | You need a deployed name or ID, such as the bucket, the CloudFront distribution, or the nameservers. Name one to print only that: `npm run infra:outputs -- route53_name_servers`.                                                                                                                                                                                                                                    | No                       |
| `npm run infra:doctor`          | A command fails, or you are on a new machine. It checks the tools, your AWS sign-in, that the state is readable, that the account matches the state, and that the secrets are readable.                                                                                                                                                                                                                               | No                       |
| `npm run infra:format:validate` | You edited Terraform files and want format problems and configuration errors caught before you apply. It reads only the files: no AWS access and no look at live infrastructure. `npm run validate` runs it.                                                                                                                                                                                                          | No                       |
| `npm run infra:format`          | `infra:format:validate` reports a format problem. It rewrites the Terraform files in standard format.                                                                                                                                                                                                                                                                                                                 | Terraform files          |
| `npm run infra:setup-user`      | You are setting up a new operator. It creates or updates the least-privilege IAM user that can run this stack. Needs admin credentials.                                                                                                                                                                                                                                                                               | Yes, one IAM user        |
| `npm run test:infra`            | You changed an infrastructure script. It runs the unit tests for those scripts.                                                                                                                                                                                                                                                                                                                                       | No                       |

`apply`, `diff`, `refresh`, `outputs` and `doctor` prepare themselves. Each one
checks that Terraform, the AWS CLI and `jq` are installed, checks your AWS
sign-in, and connects a new checkout or worktree to the state bucket. There is no
separate setup step.

For a normal infrastructure change, edit the Terraform files and run
`npm run infra:apply`. It is the only command the change needs.

To pass an argument to a command, put it after `--`, for example
`npm run infra:apply -- -auto-approve`.

The commands need AWS credentials for the account that holds the state. They read
`AWS_PROFILE` from the git-ignored `.env` when the shell has not set one. Do not
run `terraform` directly: `npm run infra:apply` is the only path that checks the
state, the account, and the changes first.

## Deploy

Deploys are handled by GitHub Actions:

- `.github/workflows/deploy.yml` (production)
- `.github/workflows/preview.yml` (PR previews)
- `.github/workflows/preview-cleanup.yml` (preview cleanup on PR close)

The production deploy first makes live infrastructure match the code on `main`, with `npm run infra:apply -- -auto-approve`, and then syncs content to S3 and invalidates CloudFront. If the infrastructure step fails, the site is not published. Preview deploys only sync content.
